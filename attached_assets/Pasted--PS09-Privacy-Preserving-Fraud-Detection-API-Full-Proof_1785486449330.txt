# PS09 — Privacy-Preserving Fraud Detection API
## Full Proof Document (Team Vortex — HackNexus)

*This document fills every section of the official PS09 documentation structure using the working, tested implementation built for this project.*

---

## Problem Statement
*(as given)*

Create a federated machine learning API allowing banks to collaboratively train fraud detection models without sharing customer transaction databases directly.

Fraud rings deliberately split transactions across multiple banks so no single institution's system flags anything unusual. Regulations (RBI data localization, GDPR, banking secrecy laws) and competitive/liability concerns prevent direct data sharing. This project builds a working federated learning system where banks jointly train one shared fraud-detection model — only the *learning* travels between banks, never the data.

## Theoretical Foundations — As Implemented

| Concept (from official doc) | How this project implements it |
|---|---|
| **Federated Learning** | 4 simulated banks each train a local `MLPClassifier` on only their own partition of data |
| **Federated Averaging (FedAvg)** | `W_global = Σ (n_k/N) × W_k` — implemented exactly as specified in `average_weights()`, weighted by each bank's sample count |
| **Distributed Machine Learning** | Training happens per-bank, independently, before combination — computation occurs where the data resides |
| **Binary Classification for Fraud Detection** | MLP with sigmoid output — fraud (1) vs. not-fraud (0) |
| **Privacy-Preserving ML** | Only `model.coefs_` / `model.intercepts_` (plain numbers) are ever transmitted — never a transaction row |
| **RESTful API Architecture** | FastAPI with `/train`, `/score`, `/status`, `/reset` — proper HTTP verbs (GET for status, POST for actions) |
| **Client–Server Communication** | Dashboard (client) ↔ FastAPI (server) via JSON over HTTPS-ready endpoints |
| **Statistical Learning Theory** | Class-imbalance-aware training (oversampling), precision/recall/F1 tracked, not just accuracy |
| **Anomaly Detection** | Fraud treated as the rare/anomalous class (~3% of data), evaluated via recall specifically |
| **Banking Regulations & Privacy Compliance** | Structural compliance with RBI data localization intent — raw data never leaves each bank's local environment |

**Not yet implemented** (see Challenges & Limitations): Secure Aggregation (cryptographic), Differential Privacy, Cryptography & Data Security beyond API-key auth.

## System Design & Architecture

```
4 Simulated Banks (private local data, never shared)
        ↓ local training (own data only, own environment)
Local Models (bank_0 ... bank_3)
        ↓ ONLY model weights (W_k) shared — never raw data
FedAvg Aggregator:  W_global = Σ (n_k/N) × W_k
        ↓
Global Model
        ↓
FastAPI Layer — /train  /score  /status  /reset
        (X-API-Key protected, per-endpoint)
        ↓
Live Dashboard — vault visual, accuracy chart, fraud checker
        ↓
Bank Client / Judge / End User
```

**Design rationale:**
- Small MLP (16→8 hidden neurons) chosen deliberately over larger architectures (e.g. the 128→64→32 used in some reference repos) so a full federated round trains in under a second — necessary for a live, clickable demo rather than a pre-recorded result.
- scikit-learn chosen over PyTorch specifically because `.coefs_` / `.intercepts_` are plain numpy arrays — the entire FedAvg averaging step is transparent and auditable, directly serving the "no black box" positioning against enterprise competitors.

---

## Model Development

- **Architecture**: MLP, input layer sized to feature count, two hidden layers (16, 8 neurons), ReLU activation, sigmoid output for binary classification.
- **Training control**: `partial_fit` used instead of `fit`, enabling manual control over federated rounds — the model can be paused, weights extracted, averaged, and resumed each round.
- **Class imbalance handling**: local oversampling of the fraud class before each bank's training step (simplified SMOTE-equivalent) — prevents the model from exploiting the ~97%-normal-transaction baseline to fake high accuracy while catching zero fraud (a failure mode we identified and fixed during development).
- **Evaluation**: accuracy, precision, recall, F1 computed per-bank and for the global model every round — recall specifically tracked because it directly measures fraud actually caught, the metric that matters most for this use case.

**Verified working test results:**
- Recall improved 12% → 96% across 10 federated rounds; F1 improved 0.08 → 0.92
- Live transaction scoring: fraud-pattern input flagged at 99.8% confidence; normal-pattern input cleared at 97.3% confidence
- Auth verified: 401 on missing/invalid key, 200 on valid key, across all three protected endpoints

## Challenges & Limitations

Stated proactively, cross-referenced against every system in the literature review — every gap below is also present in at least one reference implementation (including production Feedzai and research-stage Project AIKYA), confirming these are open problems in the field, not oversights specific to this build.

| Category | Limitation | Comparable gap in reference systems |
|---|---|---|
| **Statistical** | Non-IID data not simulated — our 4 banks are random IID splits, while real banks have genuinely different fraud distributions ("client drift") | This is the most-cited open problem in FL research generally (original FedAvg paper and all follow-ups) |
| **Security** | No defense against a malicious client submitting manipulated weights (model poisoning) | Not publicly disclosed as solved even by Feedzai; active research area (Byzantine-robust aggregation) |
| **Privacy** | Structural privacy only (raw data never sent) — no formal differential privacy or secure multi-party computation yet | Project AIKYA explicitly combines FL *with* differential privacy; we have not yet added this layer |
| **Dataset** | Synthetic data used for demo speed; real fraud is harder to separate than our generated data | Addressed in Future Scope — PaySim1 swap planned |
| **Deployment** | Render free-tier cold start (30-60s after 15 min idle) | Operational, not architectural — mitigated procedurally |
| **Auth** | Single shared demo API key rather than per-bank issued keys | Per-client key issuance is a planned enhancement, not yet built |

## Future Scope

Priority order if development continues past hackathon timeline:

1. **Swap to real dataset** (PaySim1) — replaces synthetic data, strengthens all reported metrics' credibility
2. **Differential privacy** — noise injection on weights before aggregation (highest credibility-to-effort ratio addition)
3. **Per-bank API key issuance** — move from one shared demo key to individually issued, revocable keys
4. **Non-IID simulation** — split banks by fraud *type* rather than randomly, to test FedAvg under realistic heterogeneity
5. **Byzantine-robust aggregation** — defend against a malicious or faulty client
6. **Secure aggregation protocol** — cryptographic guarantee that even the aggregator cannot see individual banks' weights in isolation

## Conclusion

Financial fraud is structurally cross-institutional, but data-sharing is structurally blocked — by regulation, liability, and competitive concern. Existing solutions either require centralizing data (reintroducing the exact risk being avoided) or are enterprise-only (Feedzai, IBM FL, Project AIKYA), leaving smaller banks, NBFCs, and cooperative institutions without a viable path to collaborative fraud intelligence.

This project demonstrates — with a working, tested, end-to-end implementation — that the core mechanism (local training, FedAvg aggregation, secured API access) is achievable without enterprise infrastructure: no GPU, free-tier hosting, ~150 lines of fully auditable aggregation logic. It does not claim to outperform production systems; it claims, and demonstrates, that the pattern is buildable and accessible outside an enterprise budget — directly targeting the research gap this problem statement identifies.
